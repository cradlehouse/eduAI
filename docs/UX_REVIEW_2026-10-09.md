# Imaje live UX review — 9 October 2026

## Purpose and scope

This review records a live walkthrough of the deployed Imaje application as:

- an organisation administrator / programme lead;
- a student on the **Last Call (test)** project;
- a first-time, untrained learner, a trained novice, and an experienced creator;
- an administrator creating a new project, **Advanced**.

The review used the real interface and a deliberately small portrait-generation test: three
reference portraits were made for TRUCKER (60 tokens) and one was selected. No other
generation, invitations, budget changes, uploads, or membership changes were made.

This is primarily a desktop review. Mobile behaviour, first-run email/invite journeys,
uploads, voice creation, video creation, consent flows, and editing/export still need their
own end-to-end tests.

## Executive assessment

Imaje now has a credible and distinctive product shape. It feels like a governed film studio
for education rather than a generic AI prompt surface. The strongest experience is the
student's path from script to a reusable character reference: the app gives them a reason to
act, a bounded choice, and a visible result that changes the state of the film.

The weakest experiences occur where the product knows the right workflow but does not make
its state model explicit. Most notably, a scene can appear complete and allow shot planning
before it has a location or cast. The administration area has the inverse problem: it exposes
too much important functionality at once without a setup sequence.

The priority is therefore not additional model capability. It is making the current workflow
more legible, more safely constrained, and easier to resume.

## What is working

### Product character and visual system

- The dark, low-chrome workspace, dot grid, glass panels, warm text, and restrained gold use
  create a distinctive studio atmosphere. The interface has a point of view without becoming
  theatrical or distracting.
- Gold is used consistently enough to carry meaning: the main next action, an active step,
  or something needing attention. Cyan successfully marks the selected character portrait.
- Creative assets are visual objects rather than rows of metadata. The Cast list uses an image,
  name, and status effectively.
- The navigation architecture inside a project is materially better than a generic sidebar:
  the small step rail establishes a production sequence: Script, Cast, Locations, Props,
  Scenes, Edit.

### Student entry and script stage

- The cohort home makes the student's current module, deadline, team, and available projects
  easy to find.
- The Script page has a strong instructional pattern. It explains the flow in context, makes
  the script visibly authoritative, and names the next blocker: `1 character or location still
  need a look. Start with Cast.`
- “Break it down” is appropriately framed as a reviewable step rather than an invisible
  automation. This supports the teaching objective: students learn how a script becomes
  production material.
- Project-level Shape, Look, and Engine show useful creative constraints without turning the
  student screen into a model configuration console.

### Character creation

- The incomplete character state is easy to identify: `TRUCKER · no look yet`.
- The application pre-populates the visual description from the script. This gives untrained
  students a viable starting point and avoids the blank-prompt problem.
- The default of three image options encourages comparison and judgement rather than accepting
  a first result.
- The live generation result was coherent: the three images plausibly depicted the same
  middle-aged trucker, with consistent cap, plaid shirt, lighting, and facial characteristics.
- Selecting `This is Trucker` gives excellent closure. The selected card receives a cyan
  border and `chosen` label; the Cast item changes to a tick; the Cast step becomes complete;
  and the page confirms `This is Trucker.`

### Organisation and project administration

- The organisation overview makes plan, seats, current generation use, invites, cohorts, and
  project-level spending inspectable in one place.
- The People page supports practical school operations: bulk invitation, cohort assignment,
  project assignment, roles, minor status, pending links, and revocation.
- The project-posting surface is concise and supports title, logline, token budget, crew cap,
  roles, open/draft status, and approval-based sign-up.
- The new **Advanced** project posted successfully and immediately appeared in the cohort's
  project list with its open state and `0 / 4` crew status.

## Key weaknesses and why they matter

### 0. Edit was not reviewed; the test project was later deleted

**Observed:** On 9 October 2026, navigating the Edit URL for the temporary **Advanced** project
returned a bare 404 page. A subsequent live project-list check confirmed that Advanced had been
deleted, leaving only SC/Warehouse and Last Call (test). The 404 is therefore consistent with a
deleted resource; it is not sufficient evidence of an Edit deployment failure.

**Why it matters:** Edit remains unreviewed and the end-to-end film workflow is still unverified.
The temporary project deletion also demonstrates why reliable walkthrough work needs a stable,
seeded acceptance-test project rather than an ad-hoc project that can disappear mid-test.

**Iteration:** Keep a protected, resettable acceptance-test project containing selected clips,
dialogue, room tone, and music. Add an authenticated route smoke test for every step-rail route
on that fixture. The eventual Edit review must cover timeline readability, track ownership,
trim/reorder behavior, undo, autosave, preview performance, export state, and instructor release
approval.

### 1. Scene readiness is not truthful

**Observed:** Scene 2 had no selected location, no cast, and no props, but the Scenes step
showed a completion tick and the `Plan the shots →` button was enabled.

**Why it matters:** This breaks the mental model that the app is a guided production process.
A student can create a shot plan before establishing the scene's world and characters. Any
resulting plan is likely to be generic, confusing, or continuity-poor.

**Iteration:** Separate “scene exists” from “scene is ready to plan.” A scene should show a
small readiness checklist:

```text
Scene 2 · Exterior diner, night

Before planning:
✓ Action / script excerpt exists
○ Choose a location
○ Add the characters in this scene
○ Add props (optional)

Plan shots — available after location and cast are set
```

The step rail should use a gold “needs setup” state until those requirements are met. Provide
an explicit alternative for valid exceptions, such as an establishing shot with no character.

### 2. The Scene screen presents too much at once

**Observed:** Scene tabs, asset drawer, small add buttons, empty location/cast/props slots,
script editing, and shot planning share the same first view.

**Why it matters:** The learner has to work out the order themselves. The screen is powerful,
but it feels like a set of raw building blocks rather than a taught exercise.

**Iteration:** Treat scene assembly as a short sequence, not a blank canvas. Focus the screen
on the currently missing prerequisite. Keep the asset drawer available, but subordinate it to
the active task. Use explicit labels such as `Set the location` and `Add the characters in this
scene`, rather than only `Where?` and `Who`.

### 3. Token cost and budget feedback are too abstract

**Observed:** The button reads `Generate 60`; the circular budget indicator changed from 66%
to 67% after generation. Neither explicitly identifies the unit or says how many tokens remain.

**Why it matters:** Cost literacy is part of the product's educational promise. Students should
learn to make intentional production choices, not merely notice a percentage changing.

**Iteration:** Every billable action should state the unit and outcome before submission:

```text
Generate 3 looks · 60 tokens
1,650 tokens will remain in this project
```

Retain the ring for at-a-glance status but pair it with a visible numeric amount, e.g.
`3,350 / 5,000 tokens used`.

### 4. The generation lifecycle has a contradictory state

**Observed:** Three finished portraits appeared while the interface still said: `Making it. It
appears here when it's done.`

**Why it matters:** Contradictory async feedback destroys confidence. A novice may wait rather
than choose; an expert may worry that a job is duplicated or incomplete.

**Iteration:** Model job states explicitly and retire them immediately when the associated
results are ready:

- Queued — `Waiting to start`.
- Making — `Making 3 looks; 1 of 3 ready`.
- Ready — `3 looks ready. Choose one.`
- Failed — `No tokens charged` or `Tokens returned`, with a human-readable reason.

### 5. The primary selection action is hidden by hover

**Observed:** `This is Trucker`, `Start from this`, and `Hide` only become visually apparent
when hovering over a result card.

**Why it matters:** New users may click the image and not discover its purpose. Hover is also a
poor default for touch screens.

**Iteration:** Keep a persistent, visible primary action on each candidate card. Secondary
actions can remain in an overflow or hover menu. Rename `Start from this` to
`Make variations from this` and show its token cost before it is submitted.

### 6. Completion rules are unclear across Look, Turnaround, and Voice

**Observed:** Choosing a Look completed Cast even though the Turnaround and Voice tabs still
appeared incomplete.

**Why it matters:** The app may be correct—turnarounds may be optional and voice unnecessary
for a non-speaking role—but it does not explain that distinction.

**Iteration:** Mark the workflow clearly:

```text
Look        Required ✓
Turnaround  Optional · useful for recurring characters
Voice       Required only when this character speaks
```

Only then is a completion tick meaningful.

### 7. The student home is informative but not directive enough

**Observed:** The learner sees module, deadline, brief, team, own project, and open projects.

**Why it matters:** It behaves as a dashboard, not a tutor. A student has to decide what to
click next even when the system knows their project blocker.

**Iteration:** Make the top card a “continue” prompt:

```text
This week: plan Scene 2
First finish TRUCKER's look, then add them to the scene.
[Continue Last Call]
```

### 8. People administration is functionally rich but operationally dense

**Observed:** One page combines bulk invitations, cohort/project assignment, age/safeguarding
declarations, pending invite links, role changes, project membership changes, minor status,
and removals.

**Why it matters:** These controls have very different impacts but receive similar visual
treatment. That makes mistakes more likely for a programme lead managing a class.

**Iteration:** Split this into two experiences:

- **Invite people:** bulk email entry, cohort, role, safeguarding check, review, send/create.
- **Manage people:** searchable member list, access, project roles, safeguarding status,
  invitations, and removal.

Add a review step before invitations are created. Treat under-18 status as a dedicated
safeguarding decision, not a peer of a normal checkbox.

### 9. Organisation setup lacks a first-run sequence

**Observed:** The admin overview exposes plans, billing, token rate, budgets, vendor keys,
people, cohorts, and invitations, but does not say what a new programme lead should do first.

**Why it matters:** Administrative success is inherently sequential. The current dashboard
assumes confidence and prior knowledge.

**Iteration:** Show a dismissible setup checklist until basic configuration is complete:

1. Create a cohort.
2. Assign instructors.
3. Invite students.
4. Post projects.
5. Allocate project budgets.
6. Publish the first module.

### 10. Project creation is permissive without explaining consequences

**Observed:** **Advanced** could be posted with only a title; it has no logline or requested
roles, a 600,000-token default budget, a four-person cap, and open sign-ups.

**Why it matters:** This is useful for an experienced programme lead, but a novice could create
an unclear, expensive, and effectively unstaffed project by accident.

**Iteration:** Preserve permissiveness for experts but add a readiness summary before posting:

```text
Advanced
No logline
No roles requested
600,000 tokens allocated
Open to sign-ups

[Post anyway]  [Complete project setup]
```

For first-time admins, make a title, short logline, and at least one crew role recommended.

## Missing capabilities or unverified journeys

These are not necessarily absent from the product; they need dedicated testing or more visible
product support.

- A clear first-run student onboarding journey that explains the project vocabulary: script,
  cast, look, location, scene, shot, take, chosen reference, and tokens.
- Mobile and touch validation, especially for hover-dependent candidate actions and drag/drop
  scene assembly.
- A robust empty-project path: create a project, add a logline/script, break it down, form a
  crew, and reach the first scene without pre-seeded content.
- Consent and release flows, particularly minors, likeness references, voice creation, guardian
  signing, and refusal states.
- Error recovery: model failure, rejected generation, loss of connectivity, double-submit,
  insufficient budget, and queued jobs.
- Project-level activity and teaching visibility: who made an asset, who chose it, what changed,
  and where an instructor should intervene.
- Stronger expert controls: reproducible settings, seed/history, model/route receipt, compare
  view, references, variation controls, and keyboard-first candidate selection.
- A clear distinction between a draft project, an open project, a crewed project, and a ready-to-
  produce project.
- Explicit project switching / resumption: “continue where you left off” rather than merely
  returning to the last project.

## Token accountability, permissions, and safety controls

### Confirmed in the implementation

The system has substantially more token and permission control than the current learner-facing
UI makes visible.

#### Token ownership and limits

- Every billable job has a **budget envelope**. It charges the project's budget where one exists;
  otherwise it falls back to the requesting user's personal budget.
- Before a job runs, the ledger reserves its estimated cost while holding the relevant budget row
  against concurrent changes. On completion it settles to actual cost; on failure or refusal it
  releases or refunds the reservation.
- The ledger is append-only and idempotent per job/kind, so retries cannot silently charge the
  same reservation twice. Job receipts retain model/version, inputs, consent basis, policy
  decisions, estimated and actual cost, and provenance.
- Project and personal token views expose total, spent, remaining, and open-reserved tokens.
  Token conversion intentionally rounds allocation down and spend up, preventing a nonzero cost
  from displaying as zero.
- Students and instructors see tokens, not the underlying monetary ledger or token-to-currency
  rate. Admins/owners can see the money and the rate.

#### Roles and data access

- The web server's normal database client runs as the signed-in user; it does not use a service
  role for normal page actions. Row-level security is therefore the intended access boundary.
- RLS is enabled across public tables and CI checks that later migrations do not add an uncovered
  table.
- Organisation membership roles are student, instructor, admin, and owner. Helper functions
  explicitly coalesce non-membership to false, avoiding accidental allow behavior from SQL NULL.
- Only an owner can grant an admin role. Owners cannot be removed through the ordinary membership
  policy.
- Generated assets and orchestration jobs are service-role work, while user writes still have RLS
  policy checks. This distinction should be threat-modelled and tested carefully.

#### Consent, minors, and release control

- Consent releases record a state of pending, signed, or revoked; deletion is not allowed because
  releases are evidence.
- Voice consent is time-sensitive: a withdrawal revokes voice use, and a later signed release is
  treated as new consent.
- A minor's status constrains the content tier and guardian-signing requirements; personal social
  accounts are prohibited for minors by policy/trigger.
- Publication is instructor-gated and records checks for consent, disclosure, integrity, content
  tier, minors, and approval.

### UX and test gaps

These safeguards are largely hidden. They should become usable product controls, not merely
backend properties.

- The live budget ring only shows a percentage. It does not show whether the charge is from the
  project or a personal allowance, remaining/reserved amount, or the user responsible for it.
- Current creation buttons display a bare number such as `Generate 60`; the unit, funding source,
  and post-action balance are not explicit.
- We have not yet exercised the refusal path, budget exhaustion, concurrent requests, failed-job
  refund, personal-budget fallback, or job receipt view in the live environment.
- We have not performed a security audit or adversarial RLS test. The implementation evidence is
  encouraging but not a substitute for role-by-role integration tests and an independent review.
- Permission state needs a human-readable explanation in product: students should know why they
  can or cannot generate, instructors should see approval duties, and admins should see who may
  alter budgets and access.

### Recommended product changes

1. Put the funding source and balance immediately beside every generation action: `Project budget ·
   1,650 tokens remaining`; if applicable, say `Your personal allowance`.
2. Show reservation status in the job card: estimated, reserved, settled/refunded, and link to a
   plain-language receipt.
3. Add a compact “Why can’t I do this?” state for permissions, consent, budget, and incomplete
   prerequisites; include the accountable role or next resolution action.
4. Give instructors an activity/approval queue and admins an audit view of membership, budget,
   token adjustments, consent state, and release decisions.
5. Add automated live integration coverage for every role × resource combination, and explicit
   tests for cross-organisation access, revoked consent, minors, duplicate submissions, and budget
   races.

## Persona-led design requirements

### New, untrained learner

Their primary need is orientation. Each screen should answer: What is this? Why does it matter?
What must I do before I can continue?

Design requirements:

- One visible primary action per screen.
- Plain-language definitions in context.
- A concrete next-step prompt based on current blockers.
- Visible costs and consequences before generation.
- Clear completion rules, including optional work.

### Trained novice

Their primary need is confidence and structured repetition. They should be able to follow a
known pattern for every character, location, scene, and shot without relearning the interface.

Design requirements:

- Consistent stage patterns: describe → generate → compare → choose → continue.
- Checklists that explain why work is incomplete.
- Short examples and suggested choices, not blank prompts.
- Safe retries and visible history.
- A quick path from a selected asset to its next use in the story.

### Expert user

Their primary need is speed, control, and reversibility. They should not be trapped by tutorial
UI or forced through unnecessary wizard steps.

Design requirements:

- Optional advanced controls rather than permanently visible complexity.
- Reuse/variation workflows from an approved asset.
- Reproducibility metadata and receipts.
- Fast navigation and keyboard support.
- Bulk and batch actions where appropriate.
- An expert override for warnings, while retaining a visible audit trail.

## Recommended delivery sequence

### Next iteration: make the existing workflow truthful

1. Implement scene readiness rules and gate shot planning appropriately.
2. Add numeric token balance and explicit token units to generation controls.
3. Fix stale generation status after result delivery.
4. Make candidate selection visible without hover.
5. Explain required versus optional Cast subtasks.
6. Add a context-aware “continue” action at cohort and project entry.

### Following iteration: make setup safe and teachable

1. Add organisation setup checklist and progress.
2. Split invite creation from member management.
3. Add invite-review and safeguarding steps.
4. Add project-posting readiness review.
5. Standardise language across the system: organisation, cohort, student, instructor, project,
   crew, scene, shot, take.

### Future: support depth without losing simplicity

1. Expert generation controls and full receipts.
2. Job queue / recovery centre.
3. Instructor intervention and student progress views.
4. Mobile-first creation and scene assembly.
5. Consent/voice/release end-to-end testing and clearer safeguards.
6. Editing/export workflow testing with real selected takes.

## Product principle to preserve

The strongest idea in Imaje is that students make production decisions, not isolated AI prompts.
Keep every future feature accountable to that idea:

> A student should always know what they are making, what it inherits, what it costs, what
> decision they must make, and what that decision unlocks next.
